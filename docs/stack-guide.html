01What this is, and what it is not

In plain terms

A person types a sentence. A language model turns it into a sequence of destinations. Conventional robotics software gets the robot to each one without falling over or hitting anything. The model never touches a motor.

The stack spans two repositories. g1_auto_navigation is the robot: localization, Nav2, locomotion, the fleet link and the operator dashboard. exp-agent is the mission layer: a small System-2 agent that holds the conversation, owns the semantic map, and calls a handful of typed tools. They meet at exactly one message type, and that narrowness is the whole safety argument.

What this is not: an end-to-end policy. Nothing here learns to walk from pixels. The model's action space is a list of named capabilities, and every one of them is validated, gated and bounded before anything moves.

Read this first

g1-016 has no hardware emergency stop. The software stop is the backstop, not a second opinion. ./g1 estop stop latches it over UDP, and docker kill on the SONIC deployer is not a stop.

02The stack, layer by layer

In plain terms

Six layers. Each one talks only to its neighbours, and each one runs at a different speed — from a sentence every few minutes at the top to a motor command every two milliseconds at the bottom.

03The boundary, and why it is structural

In plain terms

The model can say "go to the kitchen". It physically cannot say "drive forward at 0.4 metres per second". Not because we asked it nicely — because the connection it holds refuses to carry that message.

The fleet link between the host and the robot carries 32 uplink topics and 5 downlink ones. The mission service does not get all five. Its link holds a one-entry publish table, and the entry is /goal_pose. A tool call that tried to emit a velocity has nowhere to put it: /cmd_vel and /estop are unreachable by construction rather than by prompt.

The other three structural refusals

  • Destinations come from the map the robot is localized against. navigate_to's location is an enum built at schema time from the loaded places file. A hallucinated place cannot be emitted, and on a provider with strict tool schemas it is impossible rather than merely invalid.
  • A places file describing a different map refuses every destination. Walking confidently to the right label in the wrong building is the failure nothing downstream could detect.
  • One physical action per reasoning turn. Two tool calls in one turn is a protocol error, because each outcome must be seen before the next is chosen.

04A mission, end to end

In plain terms

The loop is the same one a coding agent runs. Send the goal and the current state, get exactly one action back, do it, look at what happened, repeat. The difference is that the action moves a robot, so a person may be asked first.

POST /mission/start   {"mission": "find the red bucket", "robot": "sim", "gate": "confirm"}

  1  send the mission, the tool schemas and every module's snapshot
  2  the model returns exactly one tool call
  3  validate its arguments against the schema
  4  ask the operator, if the tool moves the robot
  5  run it — navigate_to and find_object BLOCK until the walk is over
  6  attach a fresh world snapshot and fresh camera frames
  7  goto 2, until finish or request_human

Budgets bound it on four axes at once: model calls, wall clock, camera looks (every image is re-sent on every later turn, so looking is the one thing that grows a conversation without bound), and walking legs. The gate has three modes — confirm asks per step, auto does not ask, and dry-run publishes nothing at all and needs no robot, which is how a prompt change gets exercised for free.

05Three ways to move, and they are not interchangeable

In plain terms

Going to a room is one problem. Finding a bucket is a second. Walking the last metre up to it is a third. Each has its own tool, because the information each one needs is different — a map, a search, a measurement.

How close it will stand, and why that is not the number you asked for

Every standoff is measured from the centre of base_footprint, and the G1's measured footprint reaches 0.31 m in front of that origin. So a 0.60 m standoff is 0.29 m of clear air, and a "0.30 m standoff" would put the object inside the robot. Missions ask for clearance_m, the gap a person would actually measure, and the planner converts once.

You askGoal sentGap you seeWorst-case arrival
clearance_m: 0.290.60 m0.29 m0.19 m
clearance_m: 0.50.81 m0.50 m0.40 m
standoff_m: 0.3refused−0.01 mstanding on it

The 0.60 m floor is derived, not chosen: the collision monitor's stop zone (0.40 m) plus Nav2's arrival box (0.10 m) plus 0.10 m of margin. The stop zone halts the robot with nothing in any log, so a goal the checker could latch inside it is a walk that stops for no visible reason.

06Searching for what it cannot see

In plain terms

The robot faces a counter. The bucket is on the floor behind it. The robot's obstacle map says that floor is perfectly clear — because nothing has ever looked at it. Free and unseen are not the same thing, and confusing them is how a robot walks into a room it has never sensed.

Nav2's local costmap does not track unknown space on this stack, so unobserved floor reads as free. The search therefore keeps its own visibility map: a grid in the odometry frame, updated by ray-casting the camera cone through the costmap so a ray stops at the counter. The strip behind it stays unobserved. The boundary between observed-free and unobserved is the frontier, and in this scene it lines the counter's two ends — which is exactly where a person would walk.

One approval buys the whole search

find_object runs its loop on the host: ground the current frame, turn four quarters grounding each one, then repeatedly choose a standpoint, walk one Nav2 goal, and ground again. The approval names the budget — at most N legs inside R metres for at most T seconds.

The alternative, a tool per leg, was considered and rejected. It costs a reasoning turn, an operator approval and a retained image per leg; the realistic response to eight approvals per search is switching the gate to auto, which is strictly less safe than one approval a person actually reads.

It still never picks a coordinate. Candidates come from geometry and are verified against the same inflated costmap the approach uses. A cheap vision model may only choose among them, and the optional hint is words, not a position.

Two properties worth knowing

Cancelling this tool stops the robot. Everywhere else in the stack, stopping a mission does not stop a goal Nav2 already accepted. Six legs under one approval cannot inherit that, so cancelling publishes the robot's current pose as a new goal, which supersedes the leg in flight. Still one topic; the emergency stop remains the only guarantee.

A second search from an unmoved pose is refused. Measured on the pose, not on the last result. Without it a mission loops: the search reports "found, nothing moved", the approach refuses because the way is blocked, and the model — reading a refusal that says not visible — searches again.

07The two head cameras

In plain terms

The robot has two cameras on its head. One looks straight ahead and sees the room. The other is tilted 48 degrees down and sees the floor just in front of its feet. Neither can do the other's job, and for years the dashboard only showed one of them.

On the robot the pitched camera's colour has never been published — the vision node carries one hardcoded pair of preview topic names, so D455=1 swaps which pixels arrive rather than adding a feed. The simulator publishes both, under /g1/floor/, and the dashboard mounts its camera panel once per camera. Making this true on hardware is a vision-node change nobody has made.

The depth topics are separate and that is load-bearing. Aligned depth is aligned to its own colour frame. Ranging a box grounded in one camera's picture against the other's depth is wrong by the 5 cm offset and the 48° between them — and wrong in a way that grows as the object gets nearer, which is exactly the regime an approach works in.

08Knowing where it is

In plain terms

A spinning laser builds a live 3D picture of the room and matches it against a scan of the building made earlier. That match is what turns "kitchen" into a place the robot can walk to.

A Livox Mid-360 feeds FAST-LIO for odometry, and an Open3D scan-to-map step aligns that against a prior .pcd of the building. The result is a map-frame pose on /localization_3d. Two frames matter and are easy to confuse: odom is smooth and drifts, map is corrected and jumps. The local costmap lives in odom; goals are published in map.

Retained topics lie about time

The broker replays the last value of a retained topic to any new subscriber, instantly and looking perfectly fresh. A pose from a robot that has been off for an hour arrives the moment you connect. Everything that reads a pose, an e-stop state or a costmap must age it by arrival time, not trust it. A /sonic/enabled: false left behind by last week's session would otherwise refuse every goal on a robot walking happily today.

09Deciding where to step

In plain terms

Nav2 keeps two maps: a big one of the whole building for planning the route, and a small one that scrolls along with the robot for dodging what is actually in front of it right now.

Framemapodom

Rate1 Hz5 Hz
Layersstatic, LiDAR, depth, inflationLiDAR, depth, inflation
Unknown spacetrackednot tracked
ConsumerNavFn global plannerMPPI controller

The footprint is a measured eight-vertex polygon rather than a disc, which is what lets the inflation radius sit below the body radius while MPPI collision-checks the real shape. The G1 is nearly square in plan — 0.40 m deep against 0.45 m wide — so the polygon buys about 0.05 m of corridor width over the disc, not the large win it was hoped to be.

The G1 must not step backwards

The BackUp recovery is deleted from the behaviour tree. Capping velocity limits does not cover it, because the behaviour server publishes straight to /cmd_vel, bypassing both the controller and the smoother. Reversing is also the worst thing this robot can do: behind it the costmap is built from the LiDAR alone, which cannot see the floor inside about 0.90 m, and the forward-facing depth camera covers nothing back there. The recovery meant to un-stick the robot would be the likeliest way to trip it. Three recoveries remain: clear costmaps, spin, wait.

10Robot and simulator, one service

In plain terms

The real robot and the simulator are two names on the same network. Everything above the legs is identical, so a mission that works in simulation is exercising the same code that will run on hardware.

Rendering in the sim needs a GL context, and on the workstation that means X: DISPLAY=:0 MUJOCO_GL=glfw, because EGL has no driver there. The mission service opens one link per target at startup and refuses a second concurrent mission across both — two planners sharing one set of legs has no useful software arbitration.

11Reading a result honestly

In plain terms

"The robot arrived" can mean two very different things: the navigation software said so, or nobody said anything and we guessed from where the robot ended up. Every result says which.

verdict_sourceWhat it meansTrust
plannerNav2's own verdict on /goal_status. Distinguishes an abort from a slow walk.the real answer
derivedInferred from the pose converging on the goal.cannot tell a robot that gave up from one still walking
noneCancelled, lost localization, or a transport failure.nothing can be said

That field is on every result, not in the system prompt, because a model that read a caveat forty turns ago and is now looking at state: arrived will treat it as the planner's word. The same discipline runs through the tool layer: a refusal is information, not an error path. "The object is not visible", "this place is unknown", "the emergency stop is engaged" are answers to relay, not things to retry.

Known defect · unfixed

A mission that exceeds MISSION_WALL_CLOCK_S reports itself as cancelled with the summary "the operator stopped the mission". The agent cannot distinguish a stop from a timeout, because should_stop() collapses both into one boolean. In a stack that puts verdict_source on every walk precisely so nobody confuses an inference with a verdict, that string is out of character. Found 2026-09-05 during a sim run; the honest fix surfaces a distinct outcome the dashboard also renders, so it needs a decision, not just a patch.

12Traps that have already cost time

Costmap values are 0–100, not 0–255

The link carries nav_msgs/OccupancyGrid, where 100 is lethal and −1 is unknown. The 253 that means "lethal" inside Nav2's own C++ is a value no cell here can hold. A sight threshold of 253 does not make a ray-cast cautious; it makes every ray pass through every wall.

The sim's pose is stamped odom

It is the map frame by construction, and the init-pose provider normalises it. backend.status() does not. A goal built from the status publishes in the wrong frame on the one target where it matters.

A goal Nav2 accepted keeps running

Stopping a mission stops the reasoning, not the robot. Only a new goal, or the emergency stop, halts a walk in flight.

Yaw is degrees in the places file

Radians everywhere else, and it is required rather than defaulted. A waypoint in a doorway means through the doorway, and yaw is the only thing that says which way.

The local costmap is patched, not resent

The full grid arrives only when the rolling window's origin moves; between those, changes come as rectangles. Standing still — exactly when a tool inspects it — the full grid ages and the patches carry the news.

A cap equal to the source rate loses frames

Measured on this robot: a 7 Hz cap on an 8.5 Hz scan delivered 4.4 Hz. Rate caps are backstops above a source, never a second gate at the same period.

The near field is write-only memory

The LiDAR marks from 0 m but ray-traces only from 1 m, so floor speckle inside a metre accumulates and nothing erases it. A robot parked for an hour can read as boxed in. One costmap clear at the start of each navigation, never on a timer.

Images grow a conversation without bound

Every camera frame is re-sent on every later turn. A model that answers uncertainty by looking again turns a mission into an upload, which is why looks are budgeted and the cap is a refusal it can read.

13Related research

In plain terms

Almost nothing in this stack is novel on its own. It is an assembly of well-published ideas, and knowing which paper each layer descends from is the fastest way to understand why it is shaped the way it is.

Exploration and object-goal navigation

This is the literature the find_object tool sits in.

  • A Frontier-Based Approach for Autonomous Exploration Yamauchi · CIRA 1997 The origin of the idea this stack's search implements: the boundary between open space and unexplored space is where a robot should go. Nearly every autonomous exploration algorithm since is a variation on it.
  • VLFM: Vision-Language Frontier Maps for Zero-Shot Semantic Navigation Yokoyama et al. · ICRA 2024 · arXiv:2312.03275 The closest published relative of our search: build frontiers from depth, then use a vision-language model to score which frontier is most likely to reveal the target. Deployed on a Spot in a real office. Our design differs mainly in keeping the scoring inside one bounded, budgeted tool call.
  • ConceptGraphs: Open-Vocabulary 3D Scene Graphs for Perception and Planning Gu et al. · arXiv:2309.16650 Where the semantic map goes next. Our places.json is a flat dictionary of labelled poses; a scene graph adds objects, relations and open-vocabulary queries, which is what would let a mission say "the chair next to the window".
  • Hierarchical Open-Vocabulary 3D Scene Graphs for Language-Grounded Robot Navigation RSS 2024 · arXiv:2403.17846 The hierarchical version of the same idea — floors, rooms, objects — which maps more naturally onto how an operator labels a building.

Vision-language navigation models

The alternative architecture: one model that consumes pixels and emits motion. Useful to understand precisely because this stack deliberately does not do it.

  • NaVILA: Legged Robot Vision-Language-Action Model for Navigation Cheng et al. · arXiv:2412.04453 The two-level shape worth borrowing: the model emits mid-level actions in language ("move forward 75 cm") and a learned locomotion policy executes them, rather than the model producing joint commands. That seam is the same argument our /goal_pose boundary makes.
  • Uni-NaVid: A Video-Based Vision-Language-Action Model for Unifying Embodied Navigation Tasks arXiv:2412.06224 One model across instruction following, object search and following a person, from video alone. The benchmark baseline most VLN papers now compare against.
  • LightNav-0: Eliciting VLM Spatial Intelligence for Generalist Embodied Navigation Light Origins · github.com/lightorigins/LightNav-0 Reviewed 2026-09-04 as a candidate for the search layer. A 4B VLM emitting ten SE(2) waypoints from RGB plus a sentence, served over WebSocket. Its dual-channel pointing — an affordance point and an object point per frame — is a good pattern, and its prompt guide on disambiguating object phrases is directly useful to our grounder. Not adopted: it emits motion, its collision handling is RGB-only, and its vocabulary includes backwards steps this robot must never take.

The conventional stack underneath

  • The Marathon 2: A Navigation System Macenski, Martín, White, Clavero · IROS 2020 · arXiv:2003.00368 Nav2 itself. Read this before changing any costmap or behaviour-tree parameter; most of what looks arbitrary in our YAML is a documented Nav2 behaviour.
  • FAST-LIO2: Fast Direct LiDAR-Inertial Odometry Xu, Cai, He, Lin, Zhang · T-RO 2022 · arXiv:2107.06829 The odometry the robot's localization is built on. Registers raw points without feature extraction and keeps its map in an incremental k-d tree, which is why it holds up on a Jetson.
  • YOLO-World: Real-Time Open-Vocabulary Object Detection Cheng et al. · CVPR 2024 · arXiv:2401.17270 The on-robot grounder in g1_vision. Important limitation, measured on this stack: it grounds a noun with attributes and nothing more. Relations, negation and ordinals contribute nothing — "bucket that is NOT red" returned the red bucket with the highest score in the table. Constraining what the planner emits to what this can consume is a correctness requirement.

Humanoid control

  • SONIC: Supersizing Motion Tracking for Natural Humanoid Whole-Body Control NVIDIA GEAR · arXiv:2511.07820 · project page The whole-body policy this stack runs as an alternative to Unitree's built-in gait, validated on the G1. Our simulator drives it through the C++ deployer. Note the measured speed floor: below about 0.28 m/s the planner emits a reference that does not translate into motion.

Simulation and benchmarks

  • ProcTHOR: Large-Scale Embodied AI Using Procedural Generation NeurIPS 2022 · arXiv:2206.06994 The houses our MuJoCo simulator runs in. Procedurally generated, fully furnished floor plans — which is why the sim exercises occlusion and clutter rather than a box of primitives.
  • Habitat-Matterport 3D Dataset (HM3D) arXiv:2109.08238 1,000 building-scale reconstructions, and the standard ObjectNav evaluation surface. If we ever want a number for our search's success rate that means anything to an outside reader, this is the harness to quote.
  • HM3D-OVON: Open-Vocabulary Object Goal Navigation arXiv:2409.14296 The open-vocabulary version, testing category names never seen in training — synonyms and entirely unseen classes. The right benchmark for a grounder-driven search like ours.

Open questions this reading does not settle

  • Small objects on low surfaces are unreachable with the level camera alone. A cup on a coffee table has no distance at which it is both in frame and large enough for the depth image to measure. Publishing the pitched camera's colour on hardware is the fix; per-surface standoff bands are needed either way.
  • Nothing remembers what was found. Each search starts from an empty visibility map. An object layer in the places file, written whenever a grounding is confirmed, would turn most searches into lookups.
  • A place is a pose, not a region. The search radius is a placeholder until places carry their own bounds.
  • No completion rate has been measured. Everything here is reasoned or spot-checked. There is no rollout harness, so any number quoted today would be invented.

14Keeping this document alive

The source is exp-agent/docs/stack-guide.html, tracked in git beside the code it describes. Edit that file and republish to the same artifact URL — publishing a different file path creates a separate artifact and splits the document in two, which is the one mistake that quietly ends a living document.

Conventions this document keeps

  • Every number carries its provenance. measured means somebody measured it on this hardware. derived means it follows from something measured. assumed means it is the mount's intent and nobody has checked. The distinction is the point; a table of unlabelled numbers is worse than no table.
  • Two registers, every section. A plain-language lead anyone can read, then the technical body. If a section cannot be stated plainly, that usually means it is not understood yet.
  • Known defects stay in. A document that only describes what works is a brochure. Section 11 carries an unfixed one on purpose.
  • Say what is not known. "No completion rate has been measured" is more useful than a plausible figure.
